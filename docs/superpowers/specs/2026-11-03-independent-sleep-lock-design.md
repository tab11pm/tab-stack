# Независимая блокировка перед системным сном

Статус: проект согласован, реализация source и staging-проверки выполнены
в ветке `feature/independent-sleep-lock`. Пользователь выбрал отдельную службу
и работу без прерывания desktop. Host установка и живая приёмка ещё не выполнены.
Основание: [актуальный статус миграции](../../migration/current-status.md),
этап 3 [дорожной карты](2026-10-10-independent-tab-stack-roadmap.md).

## Результат

Собственная пользовательская служба следит за запросами сна logind, запускает
уже существующий Shoji locker и ждёт подтверждения secure. Она переживает
перезапуск панели и завершается вместе с независимой сессией tab-stack.
Автосон остаётся добровольным; таймеры, lid/power-key policy и глобальные
настройки logind не меняются.

Выбранная альтернатива — отдельный процесс. Обработчик внутри панели отклонён
пользователем. Заимствование монитора Omarchy не устраняет зависимость от его
оболочки и не подходит для цели самостоятельного Arch.

## Предлагаемая реализация

Python, system bus через установленные dbus-python и GLib; для чистого Arch
явно описать зависимости и проверить их до установки. Это предложение автора,
а не ранее согласованный пользователем выбор библиотек.

`tab-stack-sleep-lock.service` управляется только текущим
`tab-stack-session.target`, без зависимости от старых graphical targets.
Включение отдельное, после staging и проверки. Никакого автозапуска из
`default.target` и обращения к менеджерам других пользователей.

Монитор использует проверяемый контекст независимой сессии: UID, lease,
compositor identity и выбранное display environment. Не сохраняет полный
environment, пароль или содержимое пользовательских настроек. При невозможности
подтвердить контекст отказывается от запуска; чужие units и процессы не меняет.

На старте регистрирует обработчики сигналов system bus, получает
`Inhibit("sleep", "tab-stack", ..., "delay")` и удерживает переданный FD.
Подписка устанавливается до inhibitor; после его получения перечитывается
`PreparingForSleep`, чтобы обработать гонку запуска. Готовность службы означает
подтверждённую сессию, рабочую подписку и удерживаемый inhibitor, а не просто PID.

На `PrepareForSleep(true)` единственный worker вызывает существующий locker.
Повторные сигналы не запускают второй launcher. Успех требует проверки
`locked=true` и `secure=true` у того же проверенного locker; одного exit code
или непустого JSON недостаточно. Уже secure locker переиспользуется.
Только после подтверждения монитор закрывает inhibitor FD.

Бюджет берётся из `InhibitDelayMaxUSec`, а не фиксируется по текущему host.
Сейчас он равен 15 секундам. Начало отсчёта — получение сигнала, с резервом
на D-Bus/IPC и завершение. Launcher получает общий monotonic deadline для
проверки QML, запуска и ожидания secure: его текущие последовательные пределы
не должны складываться сверх бюджета. Ручной запуск без deadline сохраняет
прежнее поведение. Таймаут никогда не убивает уже запущенный locker.

На `PrepareForSleep(false)` монитор вновь получает delay inhibitor и проверяет
состояние, не разблокируя экран. Ошибка повторного получения, разрыв system bus
и перезапуск logind переводят готовность в degraded; переподключение не должно
создавать несколько FD или обработчиков. Завершение службы закрывает собственные
FD и workers, но не locker, panel, compositor или пользовательскую сессию.

## Отказ блокировки и граница гарантий

Delay inhibitor ограничивает задержку, а не запрещает сон. При истечении
бюджета logind может продолжить сон даже без secure. Поэтому ошибка locker
записывается как отказ защиты; она не называется отменой внешнего suspend.
Монитор не снимает inhibitor досрочно при ошибке и не вызывает повторный suspend.
После resume остаётся явная диагностика отказа; парольные данные не журналируются.

Успешные обычные сценарии требуют secure до сна. Гарантия запрета сна при отказе
locker в этот проект не входит: она требует отдельного решения о системной
политике. Привилегированный обход inhibitors также не покрывается. Приёмка
миграции не должна скрывать это ограничение.

## Интеграция и установка

Source включает монитор, unit, тесты и operator guide. Opt-in установщик
добавляет только эти файлы и проверенный способ присоединения к собственному
target; существующий installer preview остаётся без записей.

Точный механизм opt-in и readiness включить в implementation plan: существующий
session lifecycle проверяет hashes и provenance своих units. Нельзя незаметно
расширить whitelist произвольными drop-ins или засчитать active target как
готовность sleep monitor. Проверки штатных пяти служб и границы cleanup сохраняются.

Перед применением — isolated home, проверка графа units, свежие точечные backups
и сверка installed baseline. User daemon-reload/start службы относятся к отдельному
применению. Не отключать legacy sleep unit до проверки замены; не активировать
его ради теста. Global SDDM, PAM, ядро и пакетные транзакции не входят в установку.

Откат удаляет только собственное opt-in подключение после проверки manifest,
останавливает свой монитор и возвращает точные изменённые файлы. Поздние правки
приводят к отказу rollback. Откат не обещает восстановить работоспособную защиту
сна Omarchy: её служба уже была inactive в исходном состоянии.

## Проверки перед живым применением

- Fake bus/clock/locker: acquire FD, secure до release, повторные сигналы,
  already-locked, failed launcher, malformed/foreign status и общий deadline.
- FD lifecycle: resume/reacquire, disconnect/reconnect, старт во время sleep,
  остановка и повторный запуск без утечки или двойной обработки.
- Session identity и units: чужая сессия не затрагивается, optional service
  ready учитывается явно; logout останавливает монитор, reload панели — нет.
- Изолированный installer: preview без writes, preservation, точечный rollback,
  отказ на symlink/неизвестном baseline; source privacy и unit validation.
- Read-only host preflight: session check, PAM/QML/protocol, отсутствие второго
  монитора и реальный бюджет logind. Не получает inhibitor и не запускает locker.

После source/staging приёмки, в отдельное согласованное окно: неверный/верный
пароль на текущей политике, ручной suspend, собственный автосон, повторный sleep,
restart панели и применимые lid/hotplug сценарии. Наблюдать отсутствие открытого
desktop до аутентификации после resume. Отказные сценарии locker только при
проверенном TTY recovery. До этих проверок этап сна остаётся pending deployment.

## Основания API

Проверены 2026-11-03:
[logind D-Bus API](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html)
для сигналов и свойств и
[Inhibitor Locks](https://systemd.io/INHIBITOR_LOCKS/)
для FD lifecycle, resume и ограниченного delay. Документация latest не заменяет
проверку доступных интерфейсов установленного systemd 261.
