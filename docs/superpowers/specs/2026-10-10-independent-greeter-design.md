# Этап 1А: экран входа без Hyprland

Статус: пользователь выбрал существующий SDDM с X11 только для greeter.
Спецификация согласована; один override установлен и проверен на host.
Свежий системный backup сохранён. После применения журнал текущей загрузки
подтверждает запуск Xorg для greeter; пользовательский environment сообщает
Wayland/ShojiWM. Проверки display ownership, UI, relogin, cold boot и отката
ещё ожидаются; часть 1А пока не принята.
Подготовлен [план исполнения](../plans/2026-10-10-independent-greeter.md).

## Цель и разделение этапа 1

Убрать запуск Hyprland на экране входа, сохранив вход в Wayland/ShojiWM и остальные
пользовательские сессии. Рабочий стол не переводится на X11.

Этап 1 выполняется двумя самостоятельными частями:

- **1А:** SDDM greeter backend, копии настроек, вход и откат.
- **1Б:** владельцы запуска, session targets, environment и завершение сессии.
  Его отдельная спецификация составляется после получения недоступных сведений
  user manager. Не запускать graphical-session.target вручную: packaged target
  содержит RefuseManualStart=yes, а старые Omarchy wants требуют отдельного разбора.

Родительский документ: [дорожная карта](2026-10-10-independent-tab-stack-roadmap.md).
Основание: [реестр аудита](../../migration/dependency-register.md).

## Подтверждённое исходное состояние

- SDDM 0.21.0-7 и xorg-server 21.1.24-1 установлены; Xorg доступен.
- Weston и Cage не обнаружены как установленные пакеты/команды.
- `/etc/sddm.conf.d/10-wayland.conf` задаёт `DisplayServer=wayland` и
  `CompositorCommand=start-hyprland -- --config /usr/share/sddm/hyprland.lua`.
- `/usr/share/wayland-sessions/shojiwm.desktop` запускает `/usr/bin/shoji_wm --tty`.
- `/usr/local/share/wayland-sessions/omarchy.desktop` существует и запускает
  Hyprland через UWSM. Его отсутствие в `/usr/share/wayland-sessions` не означает
  отсутствие сессии: SDDM по умолчанию читает оба каталога.
- Настройка автологина указывает другую учётную запись, а не профиль текущего
  аудита. Имена этой записи не публикуются; изменение её автологина вне части 1А.
- Темы имеют несколько overrides; существующий пользовательский theme override
  сохраняется. Изменение визуального оформления greeter вне части 1А.
- Реальное состояние SDDM не подтверждено из sandbox. Пользователь подтвердил
  вход в TTY из отдельной учётной записи. Desktop user не имеет sudo;
  добавление ему административных прав вне цели. Пользователь подтвердил,
  что `sudo -v` во второй учётной записи выполняется успешно.

## Согласованный выбор

1. **SDDM + X11 greeter:** выбран пользователем для первого шага. Использует
   уже установленный компонент и один local override. ShojiWM остаётся Wayland.
2. **SDDM + Weston:** сохраняет Wayland и на экране входа; требует отдельной
   установки Weston, настройки greeter command и проверки на оборудовании.
   Не входит в согласованный первый шаг; возможен отдельным изменением позднее.
3. **Другой display manager:** не выбран; увеличивает объём миграции без
   необходимости для устранения конкретной зависимости Hyprland.

X11 здесь является допустимой частью целевой независимости: требование проекта —
отсутствие Omarchy/Hyprland, а не запрет X11. Наличие пакета Xorg не доказывает,
что SDDM greeter успешно запустится на конкретном GPU; это проверяется вручную.

## Запланированные файлы и поведение

Исходник: `dotfiles/system/sddm/zz-tab-stack-greeter.conf`.
В будущем при явной установке системной части: `/etc/sddm.conf.d/zz-tab-stack-greeter.conf`.
Точное содержимое для выбранного X11 варианта:

```ini
[General]
DisplayServer=x11
```

Не изменять packaged defaults в `/usr/lib/sddm/`, существующие theme settings,
автологин другого пользователя или global SessionCommand. Старый Wayland
CompositorCommand не используется при X11 greeter; его удаление относится к
финальной уборке, а не требуется для части 1А.

Перед установкой вычислить применимые значения с учётом всех конфигурационных
директорий и `/etc/sddm.conf`, который имеет более высокий приоритет. Если новое
значение перекрывается другим источником, не объявлять применение успешным и
не удалять чужой файл; разрешить конкретный конфликт после исследования.

Пользовательский installer не получает неявных root-операций. Системная установка
оформляется отдельной документированной операцией: backup, проверка исходных
checksums, установка одного файла с mode 644 и сохранение rollback manifest.
Перезапуск SDDM не включается автоматически в установку.

Пользовательские настройки и резервная копия остаются собственностью desktop
user. Системные действия выполняются из имеющейся административной учётной
записи, без добавления desktop user в sudo/wheel. Установка source file должна
учитывать его расположение в чужом приватном home: повышенная операция читает
только проверенный INI, а права домашней директории и backups не расширяются.

Компонент ShojiWM, Quickshell и их текущие владельцы запуска в части 1А не меняются.
Новая запись с названием tab-stack и дальнейший portable session wrapper относятся
к части 1Б. Пакеты Omarchy и Hyprland пока остаются доступными для отката.

## Подготовленная резервная копия

Создан локальный selected-file snapshot в
`$XDG_STATE_HOME/tab-stack/backups/phase1-preparation-<UTC timestamp>/`.
Сохранены 113 regular files/symlinks, один запрошенный файл отсутствовал,
заблокированных чтений не было. Копии файлов проверены SHA-256, symlinks — по target.

Состав: SDDM local/default configs, display-manager unit/link, Wayland session
entries, конфигурация ShojiWM без node_modules/backups/logs, выбранные shell
entry files, пользовательские units и target links, текущие версии пакетов и
локальная копия инструкции восстановления.

Regular backup files имеют mode 600, каталоги — 700. Manifest хранит source mode
и наблюдаемые ownership metadata; UID/GID внутри sandbox нельзя использовать
для системного chown без подтверждения host ownership. При restore требуется
восстановить нужные исходные режимы, а не mode 600 для исполняемых scripts.

Snapshot не включает package archives, EFI/initramfs или хранилища credentials.
Он не является полным backup профиля. Перед реальным изменением заново сравнить
сохранённые hashes с исходниками и сделать свежую копию при несовпадении.

## Предусловия переключения

- Пользователь подтвердил вход в TTY из отдельной учётной записи; сохраняется
  проверенный доступ к этой записи.
- Подтверждены административные действия из этой записи для одного system
  config и его удаления при откате; desktop user не получает sudo, ограничения
  sandbox не обходятся.
- Проверены актуальность snapshot, исходные modes и пригодность старого greeter
  command/бинарника. Hyprland не удаляется.
- Выяснено, какие сессии сейчас активны и кому они принадлежат.
- Перезапуск/перезагрузка согласованы отдельно в момент, когда работа сохранена.
  Изменение greeter является общесистемным и может влиять на других пользователей.

Без этих условий можно подготовить source file, документацию и проверки, но
нельзя переключать экран входа или считать часть 1А принятой.

## Проверки и ошибки

Статические проверки: точный INI, отсутствие дополнительных секций/команд,
приоритет конфигураций, отсутствие изменений автологина/темы, проверка backups,
documentation privacy и installation preview без system writes.

Живая приёмка выполняется после сохранения работы:

1. Greeter появляется на используемых outputs, принимает ввод и выбор пользователя.
2. Пользователь вручную выбирает существующую ShojiWM session и входит.
3. `XDG_SESSION_TYPE=wayland`, display принадлежит ShojiWM; greeter X11 не меняет
   тип desktop session. Отсутствие Hyprland проверяется с учётом других активных
   сессий: пользователь другой учётной записи может ещё намеренно запускать его.
4. Выход и повторный вход работают; новая панель не дублирует старую.
5. Cold boot повторяет результат. Автологин других учётных записей сохраняется.

Если Greeter не стартует: войти в проверенный TTY, удалить только добавленный
override, который manifest пометил как новый, либо вернуть предшествующий файл
из актуального snapshot, если файл уже существовал. Не удалять всю SDDM
конфигурацию. Затем штатно применить восстановление в согласованное время.
Путь rollback пока не проверен исполнением.

Если Greeter работает, а ShojiWM нет: восстановить только выявленную причину
входа; не заменять весь пользовательский профиль и не менять sleep/PAM в этой части.

## Завершение части 1А

Подготовленная спецификация и резервная копия не означают выполненное переключение.
Часть 1А считается принятой после живых проверок, сохранённых результатов и
доказанного отката. Тогда часть 1Б проектируется по подтверждённым manager states.

Документация SDDM проверена 2026-10-10: [sddm.conf(5)](https://man.archlinux.org/man/sddm.conf.5.en)
разделяет DisplayServer greeter и session directories/commands; задаёт приоритет
локальных конфигураций. Конкретные installed defaults также прочитаны локально.
