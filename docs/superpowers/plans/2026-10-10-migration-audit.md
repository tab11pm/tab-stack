# Этап 0: аудит независимости tab-stack — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Recommended here: native execution with superpowers:executing-plans.

**Goal:** Собрать доказательную карту зависимостей текущей системы и процедуру восстановления перед постепенным переходом к самостоятельному tab-stack.

**Architecture:** Аудит читает существующие файлы, пакетную базу и доступные сведения о службах. Результаты публикуются как обезличенный реестр, инструкция восстановления и матрица проверок; недоступные живые проверки сохраняют явный статус. Исполнитель не устанавливает компоненты и не меняет сессию.

**Tech Stack:** Arch/pacman, systemd/logind, SDDM, ShojiWM TSX/IPC, Quickshell QML/PAM, Python для проверки документов, Markdown.

**Spec:** [Спецификация аудита](../specs/2026-10-10-migration-audit-design.md).

## Global Constraints

- Основной режим аудита — чтение. Разрешённые результаты: локальные отчёты и обезличенные документы.
- Не выполнять установки, обновления, перезапуски, reload, блокировку, сон, logout, изменения PAM/SDDM/pacman или синхронизацию dotfiles.
- Аудит не включает ремонт обнаруженных проблем и реализацию отсутствующих функций.
- Команда с названием check не считается автоматически безопасной: сначала проверяется её код на запись, запуск GUI и другие побочные эффекты.
- Существующие незакоммиченные изменения не исправлять и не включать в коммиты аудита.
- Не читать сохранённые сетевые пароли, keyring, CLI credentials и provider settings.
- Непроверенная зависимость остаётся явно непроверенной. Запрещено превращать ошибку доступа в вывод об отсутствии службы или поддержки протокола.
- Каталог имеет режим 700, чувствительные файлы — 600.
- Публичные документы не содержат приватных данных или полных необезличенных дампов.

## Review Focus

1. D-Bus или процессы недоступны: запрет доступа должен стать ограничением доказательства, а не выводом «служба отсутствует»; проверяется в задачах 2 и 5.
2. Несколько конфигураций входа, aliases и drop-ins: наличие одного файла не определяет действующие настройки; проверяется в задаче 2.
3. Локальная сборка или пакет без доступной замены в локальной базе: отсутствие записи не означает отсутствие компонента или альтернативы; проверяется в задаче 1.
4. Несовпадение checkout и установленной конфигурации: рабочие локальные изменения и секреты должны сохраниться; проверяется в задачах 3 и 5.
5. Восстановление без сети или без GUI: инструкция должна разделять доступные локальные средства и непроверенные предпосылки; проверяется в задаче 4.

## Организация исполнения

Рабочая директория — checkout tab-stack. Перед работой зафиксировать `git status --short`
и `git diff --cached --name-only`. Не использовать `git add .`. Изменять только документы,
перечисленные в плане. Отдельный worktree для документационного аудита не обязателен;
при выборе изоляции сначала использовать соответствующий навык.

Не собирать полный вывод окружения, process arguments, журналов или домашних
конфигураций. Для пакетных данных можно сохранять полный вывод выбранных команд;
для файлов — выбранные поля или выводы. Локальные доказательства нужны только
там, где публичного обезличенного наблюдения недостаточно.

Путь локальных материалов: `$XDG_STATE_HOME/tab-stack/migration/`, если переменная
задаёт абсолютный путь; иначе `~/.local/state/tab-stack/migration/`. Недоступный путь
не заменять незаметно на репозиторий. Не записывать туда ничего, пока не нужны
локальные материалы. Чувствительные значения не выводить в пользовательский канал.

## Формат обмена между задачами

Реестр: одна запись под заголовком `### <id>`, поля `Функция`, `Компонент/владелец`,
`Запуск/область`, `Зависимость`, `Доказательство`, `Статус`, `Ограничение`, `Решение`,
`Этап`, `Предусловия`, `Проверка`, `Откат`. Для отсутствующего ограничения писать
«нет выявленного», для неприменимого поля — объяснение.

Статусы: `подтверждено конфигурацией`, `подтверждено исполнением`,
`заблокировано средой`, `не проверено`, `не применимо`.
Класс зависимости: `общая Arch`, `Omarchy CLI/IPC`, `Hyprland CLI/протокол`,
`локальная tab-stack`; в одной записи допустимы несколько классов.

Матрица: колонки `Сценарий`, `Применимость`, `Текущие доказательства`,
`Ожидаемый результат`, `Способ проверки`, `Этап`, `Локальный отчёт`.
Указываются стабильные относительные имена локальных отчётов, без личных путей.

### Task 1: Пакеты, источники, загрузка и обновление

**Files:**
- Create: `docs/migration/dependency-register.md`.
- Read: `dotfiles/sources.json`, `dotfiles/dependencies/arch.txt`, `dotfiles/docs/install.md`.
- Inspect locally: пакетная база pacman, `/etc/pacman.conf`, package hooks и службы обновления.

**Interfaces:**
- Consumes: ограничения и формат записей этого плана.
- Produces: записи `packages.omarchy`, `packages.hyprland`, `packages.desktop-runtime`,
  `packages.sources`, `updates.repositories`, `updates.hooks`, `boot.loader`, `boot.snapshots`.
  Последующие задачи ссылаются на эти идентификаторы.

- [ ] Зафиксировать исходное состояние checkout и создать вводную реестра: дата,
  область аудита, легенда статусов, перечень ограничений.
- [ ] Выполнить выборочные запросы `pacman -Qi` для Omarchy, omarchy-settings,
  Hyprland, SDDM, UWSM, Quickshell, PipeWire, WirePlumber и установленных порталов.
  Записать версию, причину установки и direct/reverse dependencies. Ошибку
  «пакет не найден» сохранять как результат конкретного запроса.
- [ ] Проверить наличие и владельца исполняемых файлов ShojiWM, Walker и Elephant
  через `command -v` и `pacman -Qo` по найденным путям; сопоставить с sources.json.
  Для локальной сборки записать подтверждённую provenance или отсутствие сведений.
- [ ] Прочитать только настройки репозиториев и относящиеся package hooks.
  Отдельно установить владельцев загрузчика, initramfs hooks и Snapper-интеграции.
  Не менять boot entries, mounts или базу пакетов.
- [ ] Для альтернатив из Arch использовать локальную синхронизированную базу
  только как предварительное свидетельство. Когда решение зависит от наличия
  замены, проверить официальный каталог Arch/AUR; записать ссылку и дату.
- [ ] Проверить записи `packages.desktop-runtime` и `packages.sources` на случай
  локальных бинарников: они не должны называться отсутствующими только потому,
  что `pacman -Qi` не нашёл одноимённый пакет.
- [ ] Просмотреть документ на личные данные и выполнить `git diff --check`.
  Коммитить только `docs/migration/dependency-register.md` с темой
  `Document package and boot dependencies for migration`.

## Приёмка плана перед исполнением

План подготовлен для просмотра пользователем. Для этого аудита рекомендуется
native execution: один исполнитель последовательно собирает и проверяет записи;
независимый reviewer проверяет итоговые документы. Это уменьшает повторный сбор
одних и тех же данных и обеспечивает единые статусы доказательств.

Запуск аудита и выбор метода исполнения согласуются после просмотра плана.
Согласование этого плана не разрешает последующие изменения системной конфигурации.
