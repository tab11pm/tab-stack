# Восстановление tab-stack при миграции

Дата: 2026-10-10. Связанные документы: [реестр](dependency-register.md),
[матрица проверок](acceptance.md), [дорожная карта](../superpowers/specs/2026-10-10-independent-tab-stack-roadmap.md).

Это подготовленная процедура, а не отчёт об успешном восстановлении.
Команды изменения системы в аудите не выполнялись. Прежде чем менять вход,
пользователь должен подтвердить доступ к TTY и административным действиям.

Отдельная [инструкция X11 greeter](../../dotfiles/docs/greeter.md) содержит
проверку приоритета SDDM, свежую host-копию и точечный откат одного файла.
Системная установка и живая приёмка ещё не выполнены.

## Предусловия первого изменения

- Проверить переход в свободный TTY, например Ctrl+Alt+F3, и вход в проверенную административную учётную запись.
  Номер свободного VT уточняется на машине. В sandbox /dev/tty2 не виден;
  это не доказательство отсутствия TTY на host.
- Проверить, что известен способ получить административные права в этом TTY.
- Держать доступную без GUI копию этого документа и нужных инструкций.
- Перед каждым изменением сохранить именно меняемые файлы, включая symlinks,
  ownership и mode; для системных файлов потребуются административные права.
- Записать старую версию бинарников/пакетов и путь к проверенным локальным архивам.
- При планируемой работе с загрузкой иметь загрузочный носитель и проверенный
  способ открыть существующие volumes, включая шифрование, если оно используется.

Вход в TTY из отдельной учётной записи подтверждён пользователем. Успешность
административных действий и остальные условия ещё не подтверждены. Изменения входа не начинать,
пока нет подтверждённого пути назад.

## Что сохранить перед соответствующими этапами

| Изменение | Файлы и компоненты | Кто восстанавливает |
| --- | --- | --- |
| Greeter / autologin | Все `/etc/sddm.conf.d/*.conf`, `/etc/sddm.conf`, если есть; выбранный session entry; пакет и бинарник greeter compositor | Администратор |
| Сессия и user services | `~/.config/shojiwm/`, относящиеся unit files, drop-ins и target symlinks в `~/.config/systemd/user/` | Desktop user; системный session entry — администратор |
| Панель | `~/.config/shoji-shell/`, `~/.config/shojiwm/scripts/start-shell`, версия Quickshell и её зависимости | Desktop user / администратор для пакетов |
| Locker | `~/.config/shoji-shell/lock/`, lock entry QML; используемые `/etc/pam.d/` policy files | Desktop user / администратор для PAM |
| Сон | Изменяемые sleep units/links и `/etc/systemd/logind.conf.d/20-inhibit-delay.conf` | Согласно расположению файла |
| Загрузка / update | Проверенные boot configs, EFI/initramfs, `/etc/mkinitcpio.conf.d/`, выбранные pacman hooks и `/etc/pacman.conf` | Администратор из работающей системы или rescue |

Не создавать и не публиковать общий backup домашней директории. Рабочие локальные
секреты сохраняются приватно и не попадают в checkout. Backup catalog имеет mode
700, credential files — 600. При сохранении конфигурации сохранять её необходимую
структуру, не раскрывая содержимое секретов в отчёте.

## Где искать installer backup manifest

Установщик tab-stack записывает `manifest.json` под
`$XDG_STATE_HOME/tab-stack/backups/`, по умолчанию `~/.local/state/tab-stack/backups/`.
Старые установки могут использовать прежнее пространство `shoji-stack/backups/`.
Наличие пригодного manifest в просмотренных путях аудит не подтвердил.
Другие XDG locations и ручные backups могут существовать; отсутствие в известных
путях не означает, что backup нигде нет.

Manifest содержит записи `target` и `backup`. Найти запись нужного компонента,
убедиться, что backup существует и соответствует состоянию перед конкретным
изменением. Прочитать JSON из терминала, без запуска панели. Абсолютные значения
из этого частного файла не публиковать.

Если `backup` не null: остановить использование компонента подходящим способом,
сохранить неработающую новую копию отдельно и вернуть старую в `target`.
Если `backup` равен null: старой копии установщик не создал; это не команда
удалить текущую папку. Не удалять пользовательские данные ради возврата к отсутствию
старого компонента. Не применять весь installer manifest, если сломался один файл.

## boot: система не загрузилась

Признак: сбой до display manager/TTY либо невозможность открыть root volume.
Предусловие: проверенный rescue medium, сведения о volumes и доступные локальные
boot backups. Их наличие и `/boot` пока не подтверждены из этой среды.

1. Загрузить rescue environment; определить фактическую систему и EFI/root volumes,
   не угадывая device names из документа.
2. Если требуется, открыть зашифрованный volume штатным способом; пароль не записывать
   в команды, документы или историю ассистента.
3. Смонтировать именно установленные root и EFI/boot volumes и использовать
   `arch-chroot` только после проверки, что это правильная система.
4. Восстановить конкретные прежние файлы/пакеты загрузки из подготовленного backup.
   Если менялся initramfs, применить штатную для этой машины процедуру его генерации
   и deployment; сейчас она не подтверждена, универсальную команду не подставлять.
5. Проверить соответствие boot entries существующим kernel/initramfs/EFI файлам.
   Затем проверить cold boot.

Нельзя обещать Snapper restore только по наличию пакета. Реальные snapshots,
их загрузка и recovery требуют отдельной проверки до работ с boot chain.

## greeter: система работает, экран входа не появился

Признак: после загрузки доступен TTY, но SDDM greeter отсутствует/неработоспособен.
Предусловие: проверенный TTY, административные права, сохранённый комплект SDDM
конфигураций и ещё доступный прежний compositor.

1. Войти через проверенный TTY; прочитать состояние `sddm.service` и ограниченный
   относящийся к отказу вывод журнала локально.
2. Проверить наличие прежнего `/usr/bin/start-hyprland` и его package dependencies,
   если откат возвращает первоначальный compositor. Восстановление одной conf
   не возвращает удалённый бинарник.
3. Восстановить только изменённые SDDM configs, включая overrides для темы и autologin.
   Проверить их приоритет; не ограничиваться одним `10-wayland.conf`.
4. Перезапустить display manager только после сохранения работы и проверки,
   что это допустимо: такое действие может завершить графические сессии.
5. Проверить greeter, ручной выбор ShojiWM и повторный вход.

Шаги 3–4 требуют административных действий. Это будущая recovery процедура,
не разрешение выполнить их при текущем аудите.

## session: greeter работает, ShojiWM не запускается

Предусловие: доступен TTY, compositor binary/runtime и выбранный component backup.

1. Проверить существование `/usr/bin/shoji_wm`, `/usr/lib/shojiwm/packages/shoji_wm`
   и `/usr/share/wayland-sessions/shojiwm.desktop`; эти части принадлежат kisa-shojiwm.
2. Восстановить относящиеся файлы `~/.config/shojiwm/` и runtime link по installer
   manifest, сохранив неработающую конфигурацию отдельно. Не заменять весь `.config`.
3. Если менялись user units или target links, вернуть только их исходное состояние.
   Перечитывание unit definitions и запуск выполняются при восстановлении,
   после проверки принадлежности нужной пользовательской сессии.
4. Повторить вход через greeter. Запуск `/usr/bin/shoji_wm --tty` прямо из свободного
   TTY — резервный кандидат, его успешность на этой машине ещё не проверена.

Проверка: compositor запускается, правильное display environment передаётся
launcher/порталам; следующий logout/login не оставляет процессов старой сессии.

## panel: compositor работает, панель отсутствует

Предусловие: доступ к терминалу либо TTY того же пользователя, исправные compositor
и Quickshell, выбранный backup оболочки. Locker рассматривается отдельно.

1. Убедиться, что не идёт активная блокировка; не убивать процессы locker.
2. Восстановить изменённые QML/script files в `~/.config/shoji-shell/` или
   `~/.config/shojiwm/scripts/start-shell`. Сохранить локальные settings и secrets.
3. Использовать существующего владельца запуска: в конфигурации ShojiWM dock
   service имеет restart=on-failure. Не добавлять параллельный запуск из systemd.
4. Если требуется ручной запуск, делать его из терминала активной Wayland-сессии
   с правильным окружением через существующий start-shell. Из произвольного TTY
   он не получает корректное окружение автоматически.

Проверка: ровно одна оболочка, рабочие launcher/portal controls; перезапуск панели
не используется как способ снять блокировку.

## locker: отказ блокировщика

Предусловие: заранее проверенный TTY и понимание последствий завершения сессии.

Если запрос блокировки отказал до secure: сохранить работу, прочитать локальные
diagnostics и восстановить выбранные locker/PAM files до следующей попытки.
Время ожидания процесса не является доказательством secure.

Если locker упал после secure: compositor может сохранить orphaned lock.
Перезапуск панели не гарантирует восстановления. Через проверенный TTY определить
нужную сессию `loginctl list-sessions`, подтвердить пользователя и compositor,
затем завершить именно её штатным способом и войти снова. Это завершит приложения
и может потерять несохранённую работу; не угадывать session ID и не завершать все
сессии пользователя. Проверка такого recovery пока не выполнялась.

Изменение `/etc/pam.d/` требует администратора; изменение locker sources — desktop
user. Восстановление policy выполняется из backup, без ослабления проверки пароля.

## packages: конфигурация восстановлена, бинарник отсутствует

Перед удалением пакета нужен проверенный локальный архив его версии и зависимостей
либо проверенный альтернативный источник. Для kisa-shojiwm дополнительно нужны
сборочный рецепт и runtime. Наличие версии в `pacman -Qi` не является архивом.

В доступном `/var/cache/pacman/pkg` совпадений по Omarchy, Hyprland, kisa-shojiwm,
SDDM, Quickshell и Limine в выборочном поиске не найдено. Другие package caches
не исследованы. Поэтому offline package rollback сейчас не подтверждён.

При восстановлении администратор проверяет архивы и транзакцию `pacman -U`
со всеми необходимыми зависимостями. Не использовать обход dependencies и не
предполагать, что текущий сетевой репозиторий содержит прежнюю версию. Копия
пользовательских dotfiles не заменяет package rollback.

## Проверено чтением и что осталось

Подтверждено наличие ShojiWM/Quickshell, session entry, SDDM configs, выбранных
systemd units и installer manifest format. Доступ к `/boot`, host bus, живой TTY
и фактическому пути Snapper restore не подтверждён. Backup catalog и пригодные
локальные package archives в известных путях не подтверждены.

Этап 0 может завершить документирование этих ограничений. Этап 1 не должен
изменять вход до живой проверки TTY и создания нужных резервных копий.
